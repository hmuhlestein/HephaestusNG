### 0.1 Where this plan corrects prior claims, rather than deferring to them

The table above credits prior art; it does not defer to it uncritically. `AUTOPILOT_REFACTOR_ANALYSIS.md` is newer, deeper on the specific areas it covers, and verified against `HEAD` as of `cb8c01a` (2026-08-14) — roughly 3.5 weeks and a large fraction of this repo's `fix:` commit history newer than `autopilot_architecture_review.md`'s last refresh (2026-07-21) and months newer than `SOLID_OO_REVIEW.md` (2026-07-01). Where the two disagree, this plan follows the newer, more specifically-verified source, and says so explicitly rather than silently picking one. Four concrete divergences found while writing this plan, each significant enough to change what Phase 1/2 below actually do:

1. **`backend_module_decomposition.md`'s `worktree_integration.py` module description is factually wrong about the current code.** It describes the cluster (`_create_integration_worktree`, `_cleanup_worktree`, `_ensure_git_excluded`, `_run_ash_scan`) as code that "calls into [the generic `WorktreeManager` class]... doesn't duplicate it." `AUTOPILOT_REFACTOR_ANALYSIS.md`'s Worktree Management §2 found the opposite: `_cleanup_worktree` calls `wt_mgr.main_repo.git.worktree("remove", ..., "--force")` **directly**, bypassing `WorktreeManager._remove_worktree`'s `require_clean` safety guard entirely — the exact guard added to close a real incident (a `security_review` agent's uncommitted fixes destroyed by a false "abandoned" sweep). `_remove_worktree`'s own docstring claims to be "the sole choke point every removal goes through"; for the shared-worktree path (the common case in production per `autopilot_architecture_review.md` §9.6), that claim is false. **Consequence for this plan:** moving this cluster into `worktree_integration.py` unchanged, as pure relocation, would relocate a live safety gap and let the new module's name/description keep asserting a property the code doesn't have. §3.1 below treats this specific cluster as an exception to the "pure move" rule.
2. **`backend_module_decomposition.md`'s `engine_client.py` module frames a duplication problem as legitimate infrastructure.** It groups `terminate_agent_direct`, `create_agent_for_task_direct`, `pause_workflow_direct`, `complete_workflow_direct`, `fail_workflow_direct` under "talk to the backend/LiteLLM I/O helpers... the architecture review's C1.2 proposal, just delayed." `AUTOPILOT_REFACTOR_ANALYSIS.md`'s Cross-Cutting Theme #2 identifies `terminate_agent_direct` and `create_agent_for_task_direct` specifically as **one half of the codebase's worst duplication pattern** — a second, parallel termination/dispatch primitive that exists only because nothing unifies it with `AgentManager.terminate_agent`/`AgentDispatchService`. Extracting these into a module named and described as durable "client" infrastructure risks the boundary calcifying into looking like intended architecture rather than a known, temporary bypass path awaiting consolidation. **Consequence:** §3.1 keeps the relocation (still useful — it's still smaller and more reviewable than 10,246 lines) but the resulting module gets an explicit header comment marking these five functions as Phase 2 consolidation targets, not a finished abstraction.
3. **`autopilot_architecture_review.md` §11.1's "Done" table is a shipped-feature log, not a correctness audit — several "Done" rows have live bugs inside them that this plan's source analysis found independently.** "Worktree isolation core" and "§9.6 per-design integration worktree" are marked Done; `AUTOPILOT_REFACTOR_ANALYSIS.md`'s Worktree Management section found, inside exactly that area, four independent worktree-removal implementations, three independent and behaviorally-different merge-conflict-resolution strategies (one confirmed dead in production), and the safety-guard bypass in point 1 above. "Hybrid spec gate (§9.1)" is marked Done; the task-creation-claim race it depends on (`fire_spec_gate_if_ready`'s claim path) has been independently patched **four more times** since (`75e1e52`, `45dd5a2`, `85fc3c5`, `fe9a141`), all landing after this table's last refresh. **Consequence:** this plan treats every row in that table as "shipped," full stop — not as a signal the underlying code is duplication- or bug-free. Nothing in §3-6 below skips auditing a subsystem because an older doc calls it Done.
4. **`SOLID_REFACTOR_ADVERSARIAL_REVIEW.md`'s "✅ Fixed" status is scoped to the 22 findings it lists, not to the general health of the files it touched.** Its commit `1998a11` cleanly extracted `OrphanSessionReaper` from `MonitoringLoop` — verified bug-free *for that extraction* by the review's own 8-pass audit. But the `datetime.now()`-instead-of-`datetime.utcnow()` bug this plan's source analysis found at `orphan_reaper.py:111,125,147` was already present in the code being extracted and was outside that review's scope (it wasn't a bug the *extraction* introduced, so the extraction-focused audit had no reason to flag it). **Consequence:** a clean, verified refactor of a file does not retroactively certify the file's pre-existing logic — this plan's Phase 0 characterization tests (§2) exist specifically because "this was refactored and verified once" is not the same claim as "this has no bugs."
5. **A passing test suite can itself be the thing masking a bug, not just failing to catch one — found via the bug-fix-history pass, not the current-code read.** `_trigger_arbitration` inserted a `Task` row with a `created_by_agent_id` that had no corresponding `Agent` row, and an `Agent.agent_type` value (`"arbitration"`) the DB's own `CHECK` constraint never permitted. Every dispatch in production raised `IntegrityError`, swallowed by a catch-all logged at `DEBUG` — invisible at the default log level — for an unknown period, discovered only via a live incident where one workflow re-evaluated to "needs arbitration" every ~15-20s for **over 30 hours** (1,180+ failed attempts, zero arbitration tasks ever created). The reason the existing test suite never caught this: `test_advance_phases.py`'s own **autouse** `_seed_sentinel_agents` fixture pre-created exactly the `Agent` row production never had, so every test ran against a condition production didn't satisfy. Fixed across three same-afternoon commits (`d0f7411`, `6b37cb7`, `fd926cc`) — see the analysis document's Bug-Fix History §3 for the full trace. **Consequence:** this is a distinct risk from point 4 above (a verified-clean refactor with an untouched pre-existing bug) — here the test suite was actively, structurally incapable of exercising the failure mode at all, by construction of an autouse fixture. Principle #9 (§1) exists because of this specific incident.

6. **Two of this repo's own design docs directly contradict each other, and this plan's testing strategy (§8) was, until this revision, unknowingly standing on the side that loses.** `docs/SAFE_RESTART_DESIGN.md` (implemented in commit `271745f`, and described favorably in the analysis document's Workflow Termination & API Surface section with no caveat) has the backend's `shutdown_event` notify in-flight agents, sleep `SAFE_RESTART_GRACE_SECONDS` (10s), then drain each running service — uvicorn is meant to stay alive through all of it. `docs/process_lifecycle_audit.md` (finding S8, added 2026-08-15) traces `heph stop`'s own escalation timing — SIGKILL after 5s at the port-kill stage, 2.5s at the PID-file stage — and shows it fires *before* the drain SAFE_RESTART depends on can complete, on every single `heph stop`/`heph restart`, unless the backend happens to be SIGTERMed some other way that bypasses the CLI entirely. Confirmed directly (not just cited) for this revision: `src/cli/commands/restart.py` is exactly `stop_run(args)` then `start_run(args)` — so `heph restart`, the command this plan's own §8 testing strategy invokes after every phase, is the exact command the audit shows can never let SAFE_RESTART's drain finish. **Consequence:** §8's "per-phase, live: `heph restart`, then Phase 0's smoke script" step is not wrong to use `heph restart` — it's still the right way to catch import/wiring breakage — but it should not be read as evidence that a graceful, state-preserving restart happened; it wasn't testing that, and per this finding, mostly can't. §10's self-hosting risk bullet is updated accordingly.

None of this invalidates the prior docs' core value — the module boundaries in `backend_module_decomposition.md` are still the right *starting point* for six of its eight orchestrator modules, and the adversarial-review methodology in `SOLID_REFACTOR_ADVERSARIAL_REVIEW.md` is still the right verification process (adopted wholesale in §8). The correction is narrower and more useful than a wholesale rewrite: **treat prior status labels as claims to re-verify against newer evidence, not facts to build on unchecked** — exactly the standard `AUTOPILOT_REFACTOR_ANALYSIS.md` was held to when it was written (see that document's own Coverage Notes on not assuming novelty either). §3's Phase 1 plan below reflects points 1-2 directly; point 3's implication (re-audit, don't skip, anything marked Done) is threaded through Phases 2-4; points 4 and 5 are why Phase 0 exists at all and why principle #9 (§1) is non-negotiable, not aspirational; point 6 is why §8's `heph restart` step now carries an explicit scope caveat rather than an implicit assumption.

**Feeding this back:** correcting `worktree_integration.py`'s module description in `backend_module_decomposition.md` itself, and adding a caveat line to `autopilot_architecture_review.md` §11.1's "Worktree isolation core" / "§9.6" / "Hybrid spec gate" rows pointing at this document, is included as a Phase 1 deliverable (§3.3) — not left as an implicit inconsistency for the next reader to rediscover the way this plan's own drafting just did.

## 1. Guiding principles (non-negotiable for every phase below)

1. **Decomposition and bug-fixing never share a commit.** `backend_module_decomposition.md` states this explicitly for its own scope ("If you notice a bug while moving code... note it, don't fix it here") — this plan applies the same rule to *every* extraction in every phase. A move that also fixes something is two changes wearing one commit; if it breaks, `git bisect` can't tell you which half.
2. **One extraction or one fix = one commit.** Never batch multiple modules or multiple bug fixes into one commit, per the same document's sequencing note (§5 there). This is how a 15-module decomposition or a 15-bug-fix pass stays bisectable.
3. **No backward-compatibility shims.** Per this repo's own CLAUDE.md ("Forbidden... no feature flags or backwards-compatibility shims") and `backend_module_decomposition.md`'s explicit call-out: a moved symbol's old import path should raise `ImportError`, not silently re-export. Fix every call site; don't paper over the move.
4. **Every primitive consolidation is preceded by a regression/characterization test capturing current behavior**, especially for the ~45 historically-fixed races documented in `AUTOPILOT_REFACTOR_ANALYSIS.md`. The single biggest risk in this entire plan is silently re-introducing one of those already-fixed bugs while "cleaning up" the code around it. A test that fails on old behavior and passes on the consolidated primitive is the only way to know the fix carried through the merge, not just moved the bug's address.
5. **Mechanical moves are scripted, not hand-copied**, per `backend_module_decomposition.md` §3.3's method (AST-parse, extract by `.lineno`/`.end_lineno`, byte-for-byte reassembly check) — applied to every large-file split in this plan, not only the two files that document specs.
6. **Every phase ends with the adversarial-review gate** described in §8, mirroring `SOLID_REFACTOR_ADVERSARIAL_REVIEW.md`'s proven process, before the next phase starts.
7. **Preserve intent, not just behavior.** Where a historical commit's inline comment explains *why* a defensive check exists ("observed live: ..."), that rationale must survive the refactor as a code comment, docstring, or test name — not get silently dropped because the surrounding code moved. `AUTOPILOT_REFACTOR_ANALYSIS.md`'s Orchestrator Core §7 catalogs dozens of these; they are the accumulated cost of real incidents and are not safe to treat as boilerplate to trim.
8. **This is a self-hosting system.** Hephaestus's own pipeline can be used to build Hephaestus (per `autopilot_architecture_review.md`). A decomposition that breaks import resolution doesn't just fail tests — it can brick the tool's own ability to run itself. Every phase below ends with `heph restart` + a live smoke check (§8), not just a green test suite.
9. **No autouse fixture may seed away the exact condition a test is supposed to exercise.** Per §0.1 point 5: the arbitration subsystem was completely non-functional in production for an unknown period (a DB `CHECK`-constraint violation on every dispatch, swallowed at `DEBUG`) while its own test suite passed the whole time, because `test_advance_phases.py`'s autouse `_seed_sentinel_agents` fixture pre-created the exact `Agent` row production never had. Every characterization test written in Phase 0, and every red-then-green test in Phase 3, must be checked against the fixtures it inherits (autouse or explicit) for this specific failure mode: does the fixture set up a precondition the real code path is responsible for creating itself? If so, the test is verifying the fixture, not the code — write the test against the minimal, code-created state instead, or explicitly assert the code creates whatever the fixture would otherwise silently supply.

## 2. Phase 0 — Safety net (before touching anything)

**Goal:** make it possible to *know*, not guess, whether Phases 1-4 preserved behavior.

1. **Route-count/path-set guardrail tests** for every router this plan will split (§3.1, §3.2's table): a test asserting `len(router.routes)` and the exact path set match a hardcoded baseline captured from the *current* code, before any split. `backend_module_decomposition.md` §6 already specs this for the `autopilot_api.py` → `src/mcp/autopilot/` split (52 routes); extend the same pattern to `src/mcp/api.py`'s 42 routes and `src/mcp/agents_api.py`/`tickets_api.py`/`messaging_api.py` if those are touched in Phase 1 (they are not currently speced for decomposition — see §3.2's scope note).
2. **Characterization tests for the primitives Phase 1's exceptions and Phase 2 will consolidate**, written against *current* behavior before either starts:
   - Agent-termination invariant: a parametrized test hitting every one of the ~21 confirmed termination call sites (`AUTOPILOT_REFACTOR_ANALYSIS.md`'s Agent Lifecycle Management §2 table + the two new `src/mcp/api.py` sites), asserting `status/current_task_id/terminated_at` end in the invariant-correct state. This test is *expected to fail* at 3 of the ~21 sites today (the two `terminated_at` gaps in `api.py`, the `current_task_id` gap in `monitor.py`) — that's the point: it turns three silent bugs into three visible red tests, fixed in Phase 3 (§5, Tier 1 items 5-6), not accidentally re-broken during Phase 2's consolidation (§4.2).
   - Task-creation-claim races: the existing `test_maybe_retry_failed_tasks_is_claim_protected`-style tests referenced in the analysis doc, extended to cover `fire_spec_gate_if_ready`'s claim path explicitly (the `fe9a141` fix). This was meant to be the gate for **Phase 1's `phase_transitions.py` exception (§3.1)** — **verified 2026-08-16 that gate never actually fired**: the module's extraction shipped before these characterization tests existed, not after, so the exception's own precondition ("safe to consolidate because behavior is characterized first") was never satisfied, and the consolidation itself didn't happen either. The characterization tests now exist (written this revision, retroactively) covering all three staleness-fallback copies, both retry implementations' overlap behavior, and confirming arbitration dispatch's existing coverage is adequate — but they're gating Phase 2 work now, not Phase 1's already-shipped (and unconsolidated) extraction. §4.1 carries the full scope accordingly, not just the `fire_spec_gate_if_ready` migration.
   - Worktree removal safety: a test asserting `_cleanup_worktree`'s raw `git worktree remove --force` call path (the one bypassing `_remove_worktree`'s `require_clean` guard) is what **Phase 1's `worktree_integration.py` exception (§3.1)** closes — capture the current unsafe behavior first so the fix is provably a fix, not just a refactor that happens to also change behavior nobody asked for. (§4.4 still handles the separate merge-conflict-strategy consolidation, which this specific test does not cover.)
3. **A held-out smoke script**: `heph start` a throwaway test project, queue one trivial design, and confirm it reaches at least one `goto`/`retry` cycle and one clean phase completion before Phase 1 starts. Re-run this exact script after every phase in §8 — it is the cheapest end-to-end signal that decomposition didn't silently break the control loop, and it's what `autopilot_architecture_review.md` §11.2's "Run A/Run B" smoke-run methodology already established as this project's own bar for "does the pipeline actually work," not just "do imports resolve."

**Do not proceed to Phase 1 until Phase 0's guardrail tests exist and are checked into version control.** They are the only thing standing between "the refactor preserved intent" and "the refactor happened to not crash."

## 3. Phase 1 — Decomposition, mostly pure, two deliberate exceptions (decompose)

**Default rule for this phase, inherited from `backend_module_decomposition.md` §7: zero behavior change. If you notice a bug while moving code, log it for Phase 3 — don't fix it here.** This default holds for six of the eight orchestrator modules and all seven `autopilot_api.py` modules below. It is **deliberately not applied** to `worktree_integration.py` and `phase_transitions.py` — see 3.1's callouts — because for those two specifically, treating the move as behavior-preserving would be preserving a bug (§0.1 point 1) or splitting a single tightly-coupled duplication cluster across a "moved now, deduplicated later" seam that adds a second risky touch to the exact same ~30 lines for no real bisectability benefit (§0.1's `phase_transitions.py` reasoning below). Applying one rule uniformly to eight modules that don't share the same risk profile is exactly the kind of unexamined deference §0.1 is about — the rule is right for six of them and wrong for two, so it's applied that way, not uniformly.

### 3.1 Execute the existing plan, module by module, re-verified rather than re-derived

Run `backend_module_decomposition.md`'s §3.1/§3.2 symbol-to-module mapping — it is exhaustive, line-range-verified, and already accounts for the two proximity-misleads and the one gap a prior draft missed. **Before starting, re-run its own freshness check**: `grep -n "^def \|^class \|^async def " src/autopilot/orchestrator.py` and the equivalent for `autopilot_api.py`, and reconcile the new symbol count against the doc's `117`/`52`-route baselines. Both files have grown since verification (orchestrator.py: 8,372 → ~10,246 lines per this plan's source analysis; `autopilot_api.py`: 3,980 → ~5,724 lines) — new top-level functions almost certainly exist that aren't in the doc's table yet. Treat any new symbol as belonging to whichever module cluster its behavior most resembles, using the doc's own cluster descriptions as the classification rubric (updated per the two callouts below), and add it to the mapping before running the extraction script — don't let it fall through to the `__init__.py` "remaining" catch-all by default.

Sequencing, per that doc's own §5: `state.py → engine_client.py → policy.py → queue.py → worktree_integration.py → features.py → reporting.py → phase_transitions.py` (orchestrator side), then `_shared.py → control_routes.py → queue_routes.py → project_routes.py → feature_routes.py → message_routes.py → intervention_routes.py` (API side). Each module is still its own commit per principle #2 — the two exceptions below change *what* that commit contains for those two modules, not the one-module-one-commit discipline.

**Exception 1 — `worktree_integration.py`: fix the safety-guard bypass as part of the move, don't relocate it unchanged.** Per §0.1 point 1, `_cleanup_worktree`'s raw `git worktree remove --force` bypasses `WorktreeManager._remove_worktree`'s `require_clean` guard. Moving this function into its new module without also routing it through the real guarded primitive would (a) contradict the new module's own description of "calls into WorktreeManager, doesn't duplicate it" the moment it's written, and (b) require a second, separate commit shortly after to fix the exact lines just moved — not a bisectability win, just deferred cleanup with extra steps. This module's extraction is scoped together with the worktree-primitive work that would otherwise be Phase 2 item §4.4, landing as this module's own commit(s) rather than split across two phases. Phase 0's worktree-removal-safety characterization test (§2 item 2) gates this commit specifically. **Status: done, verified 2026-08-16** — `_cleanup_worktree` (`worktree_integration.py`) now calls `wt_mgr._remove_worktree(str(worktree), require_clean=True)` and checks `worktree.exists()` afterward to log the actual outcome, rather than an unconditional raw `git worktree remove --force`. ### 4.12 Queue-dispatch claim & offload-race primitive (found and closed same-day, 2026-08-21)

**Current state / how this was found:** commit `12e12ee` offloaded `process_queue`'s DB work (capacity check → dequeue → phase resolution → enrichment write-back → `mark_assigned`) into `run_in_executor`, closing a real event-loop-blocking problem — this endpoint fires on every task dispatch, unlike the periodic background sweep it mirrored (`background_phase_advancement_sweep`, which already had the same treatment). But the sequence it moved — `should_queue_task` → `get_next_queued_task` → `dequeue_task` — had no DB-level atomicity of its own; it had only ever been safe because nothing in it awaited, so the single-threaded event loop could never interleave two concurrent calls mid-sequence. Moving it onto a real `ThreadPoolExecutor` removed that accidental protection: two overlapping `process_queue()` calls could now run genuinely concurrently on different OS threads and both select-then-dequeue the *same* queued task, dispatching two agents onto one task — the same claim-primitive bug class §4.1 already covers for task-creation, this time in the queue-dequeue path.

**Fix, in three commits landing the same day the regression was introduced:**
- `0224543` added `QueueService.claim_next_queued_task()`, serializing `should_queue_task`/`get_next_queued_task`/`dequeue_task` under a new `threading.Lock` (`_dequeue_lock`) — mirroring the existing `_reservation_lock` pattern already used for the identical race class in `try_reserve_cli_model_slot`/`release_cli_model_slot`. `background_loops.py`'s dequeue-and-resolve helper now calls this one atomic method instead of the three separate calls. A 20-real-thread regression test proved the race (reverting to the naive three-call version fails it 5/5 runs) and proved the fix (clean after restoring it).
- `47d95a6` widened the same lock to three more unlocked queued-task mutation sites found while tracing a live incident (`dequeue_task` itself, `boost_task_priority`, and a new locked `QueueService.cancel_queued_task` for `cancel_queued_task_endpoint`'s status write, which had been landing inside the claim's select-then-dequeue window). The same commit also fixed two related but distinct bugs surfaced by the same live incident (workflow `ca539a75`): an arbitration task's own completion re-firing the generic phase gate against already-consumed artifacts (`consume_gate_artifacts` deletes them after every goto) instead of routing to `_maybe_resolve_arbitration`, producing redundant repeat arbitration cycles; and `mark_phase_complete` treating a transient SQLite "database is locked" error as a phase-flow `action="arbitrate"` decision via a blanket `except`, discarding an arbiter's already-decided "continue" — now retried from a fresh session (bounded, backoff) before falling through to arbitration.
- `7a42d2e` found three more call sites still mutating a `"queued"` task's row with no lock at all (`cancel_task_endpoint`, `cancel_workflow`, `pause_task_endpoint`), added `QueueService.pause_queued_task` as the pause-side sibling of `cancel_queued_task`, and hardened `claim_next_queued_task` itself with a defense-in-depth check: `dequeue_task` now returns `bool`, and the claim path treats a `False` return (task changed state or was deleted between select and dequeue, by any caller, locked or not) as "not actually claimed" rather than handing `process_queue` a task it doesn't own — holding even against a future caller that forgets to take the lock. Flagged, not fixed here: `stop_workflow` only reset `"assigned"`/`"in_progress"` tasks, never a workflow's `"queued"` ones — a pre-existing product-semantics gap, addressed separately (see §4.8's 2026-08-21 follow-up below), not a concurrency bug in this item's scope.

**Verification:** `test_queue_service.py`'s new `TestClaimNextQueuedTaskDefenseInDepth`/real-thread lock-contention test classes; 85→123→205 tests passing across the three commits with zero regressions at each step, cited in each commit message.

**Status: done, shipped 2026-08-21 (`0224543`, `47d95a6`, `7a42d2e`).** Not previously named in this plan — found and closed same-day as a direct consequence of `12e12ee`'s otherwise-correct offload fix, the "consolidation makes a latent bug live" pattern §1's guiding principles already warn to watch for.

## 8. Testing & verification strategy (applies to every phase)

This mirrors `SOLID_REFACTOR_ADVERSARIAL_REVIEW.md`'s proven process, since it's the one time this exact class of refactor (large-scale internal restructuring, live production-shaped system, self-hosting) has actually been executed and verified in this codebase:

1. **Per-commit:** run only the targeted test files for whatever cluster/primitive just changed (per this repo's stated preference — see [[feedback_targeted_tests_only]] in this session's own memory), not the full suite, immediately after each commit. `ruff check`/`mypy` after each extraction — moved code is exactly where a stray unused import gets left behind (per `backend_module_decomposition.md` §6).
2. **Per-phase:** an adversarial review pass before moving to the next phase — 8 parallel finder passes over that phase's full diff: line-by-line scan for introduced bugs, a removed-behavior audit (did any branch/check silently disappear in the move), cross-file call-site tracing (every import updated), a language-pitfall scan (Python-specific footguns: mutable defaults, late-binding closures, `is`-vs-`==` on new code), wrapper/proxy correctness (delegated methods preserve their original signatures), reuse/simplification opportunities the phase's own changes newly exposed, efficiency/altitude concerns, and a final gap sweep. This is exactly `SOLID_REFACTOR_ADVERSARIAL_REVIEW.md`'s method, applied to each phase here instead of one session.
3. **Per-phase, live:** `heph restart`, then Phase 0's smoke script (queue a trivial design, confirm at least one `goto`/`retry` cycle and one clean completion) — imports resolving and unit tests passing is necessary but not sufficient; this project's own `autopilot_architecture_review.md` §11.2 found real defects (the spec gate silently not firing) that only a live run surfaced. **Scope caveat, per §0.1 point 6:** `heph restart` here is being used to catch import/wiring breakage from the phase's own diff — it demonstrates the new code loads and the pipeline can reach a clean state *from a cold start*, not that the backend restarted *gracefully* out of an in-flight state. `docs/process_lifecycle_audit.md` (S8) found `heph stop`'s own SIGKILL escalation fires before SAFE_RESTART's drain can finish on essentially every invocation, so this smoke check should always run against a backend with **no live agents/workflows in flight** (queue the trivial design fresh, don't restart mid-pipeline) — otherwise a "successful" restart may be validating a state that was actually SIGKILLed, not drained, which is a different and weaker guarantee than the step's original intent implied.
4. **Full suite, before merging each phase to the trunk this plan builds on:** the complete `pytest` run, not just targeted files — the phase boundary is the right place for the more expensive check, not every commit.
5. **Regression tests are permanent, not scaffolding.** Every characterization test from Phase 0 and every red-then-green test from Phase 3 stays in the suite after the phase completes — they are now the guardrail against the *next* refactor re-introducing the same bug class, which is exactly the failure mode this plan exists to break (a bug fixed 4-8 independent times is a bug with no permanent regression coverage tying the fix to the invariant it protects).
6. **Audit every new or touched test's fixtures against principle #9 before trusting it green.** A test suite that passes is not evidence a code path works if an autouse fixture silently supplies a precondition the code path is itself responsible for creating — this is not a hypothetical concern for this codebase specifically (§0.1 point 5). When writing or reviewing a characterization test in Phase 0, or a red-then-green test in Phase 3, explicitly check: does every fixture this test depends on (autouse or explicit) get created by the *code under test*, or is the fixture quietly standing in for something the code is supposed to do and doesn't? If the latter, the test is validating the fixture, not the code.

**Two risks that apply across every phase, not just one row above:**

- **This is a self-hosting system** (principle #8). If Autopilot itself is used to execute any part of this plan, a broken intermediate state in Phase 1 (e.g., mid-decomposition, imports not yet fully fixed) could leave the tool unable to run its own pipeline to fix itself. Mitigation: Phase 0's smoke script (§2 item 3) is not optional, and should be re-run after *every commit* during `phase_transitions.py`'s extraction specifically (§3.1's XL item), not just at phase boundaries — the cost of a smoke-run is far lower than the cost of discovering the self-hosting loop is broken only after several more commits have landed on top of the break. **Sharpened by `docs/process_lifecycle_audit.md` (§0.1 point 6):** if this plan is executed *by* Autopilot against itself and a `heph restart` happens to land while a real pipeline is active (not just this plan's own smoke-test design), the audit's S8/S9 findings mean the restart is likely to SIGKILL mid-drain rather than pause cleanly, and per S9 a standalone orchestrator process (if one is running) survives `heph stop` entirely, racing the freshly-restarted backend against the same DB. Neither finding is something this plan fixes (out of scope, §7) — but anyone executing this plan against a live self-hosted run should confirm no other Autopilot pipeline is mid-flight before any `heph restart` this plan's own process calls for, not just before the smoke-test design.
- **DB schema changes need a real migration, not just code deletion.** Only one item in this plan touches the schema directly (§6's `SteeringIntervention` table, if the "delete" branch of that either/or is chosen over "wire it up") — flagged again here because it's the one item in an otherwise pure-code-change plan where `git revert` alone does not undo the effect; a migration's `down_revision` (or this project's equivalent rollback mechanism) needs to exist and be tested *before* the forward migration ships, not written reactively after a rollback is already needed.

**Calibration: the two most severe incidents the bug-fix-history pass documented, both already fixed, both evidence for why the Phase 2 items above are worth the effort sized above rather than deferred.** Neither requires action from this plan — they're cited here because "M effort, consolidate this primitive" reads as abstract housekeeping without knowing what the un-consolidated version actually cost in production:
- **A 30-hour, 1,180-attempt arbitration outage** (§0.1 point 5): a DB constraint violation on every arbitration dispatch, invisible at default log level, undetected by a test suite whose own autouse fixture masked the exact condition production lacked. This is the concrete argument for principle #9 and for treating §4.9's schema-resolver consolidation as high-value despite its XL size — schema/constraint mismatches in this codebase have a demonstrated path to multi-hour production outages, not just code-review nitpicks.
- **A 162-goto runaway loop** burning an entire arbitration budget on an unwinnable cycle (`21fa097`, in §4.9's gate-scorer-brittleness cluster): a scorer's mechanical list-emptiness rule directly contradicted the phase's own prompt instructions, so a correctly-behaving agent's output was rejected, sent back for identical regeneration, and rejected again, repeatedly, until the budget exhausted and a live development task was killed as collateral damage. This is the sharpest evidence in the whole bug-fix-history pass that §4.9's "shared schema per phase" consolidation is closing a real, severe, already-demonstrated failure mode — not a hypothetical one.
